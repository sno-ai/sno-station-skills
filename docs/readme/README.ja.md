**AI エージェントは、とびきり優秀な新人です。ただし、面倒を見てくれる先輩はひとりもいない。このスキル集は、何度もリリースをくぐり抜けてきたチームの作法を、エージェントに身につけさせます。** 作る係とレビューする係は、別のエージェント。クォータが尽きる前に引き継ぎメモを書き、別のエージェントがまったく同じコミットから続きを拾う。実際に動かして証明するまで、「終わりました」とは誰にも言わせない。そして毎晩その日をふりかえり、新しいルールを提案します。採用するかどうかは、あなたが決めます。

対応エージェントは **Claude Code、Codex、Cursor、Hermes Agent**、そして OpenClaw。エージェントが実行できるスキルはフル機能で、実行しきれないものは機能を絞った形でインストールされます。

スキルはすべてプレーンテキスト。読めるし、コピーできるし、書き換えられます。[Sno Station](https://github.com/sno-ai/sno-station) が、いま使っているエージェントにそのまま入れるスキルであり、私たち自身が Sno Station を作るために毎日使っているスキルでもあります。

## あなたの毎日はこう変わる

使い方はこれまでどおり。好きなエージェントで、いつもの仕事を続けてください。そのうえで、こう変わります。

1. **変更が終わって、誰かに見てほしいとき。** 「peer-review this」と言うだけ。別ベンダーのレビュアーが
   予備知識ゼロで読み、実際に使うと何が壊れるかを報告します。作者は根本原因を直し、レビューが
   きれいに通るまで何ラウンドでも繰り返します。
2. **寝る前に長いジョブを流すとき。** 「arm rotate-agent」と言っておく。夜中に作業中のエージェントの
   クォータがしきい値まで減ったら、別ベンダーの新しいエージェントにタスクを渡します。引き継ぎ内容の
   確認が済むまで、ファイルには一切触れません。
3. **決まった時刻にやってほしいとき。** 時刻を言うだけです。「明日の 9 時にビルドを確認して」
   「毎朝 7 時にレポートを書いて」。その時刻になるとエージェントが動き出します。会話を開いていても
   閉じていても同じです。予定は `sno heartbeat --due` で確認できます。Sno Station のこの部分は
   Finish と呼ばれていて、詳しくは[ガイド](https://github.com/sno-ai/sno-station/blob/main/docs/finish.md)にあります。
4. **戻ってきたとき。** 「away brief」と言えば、最大 60 行の 1 ページ。終わったこと、止まっていることと
   その理由、あなたの返事待ちのこと、使ったクォータがひと目でわかります。
5. **誰かに仕事を任せたいとき。** 「write a charter」と言えば、ファイルがひとつ出てきます。何を納品
   するのか、何に手を出してはいけないのか、あなたがもう決めたことは何か、そして成功条件をそれぞれ
   どう証明するのか。あとはどのエージェントでも `deliver` でき、成功条件はすべて記録に残る実際の
   実行で証明されます。
6. **毎晩、チームでふりかえり。** 夜のループが全エージェントのその日のセッションを読み、繰り返される
   ミスを見つけ、教訓とスキルの変更を提案します。朝、気に入ったものを
   `sno rem-reflect accept <id>` で採用してください。その accept がない限り、何も変わりません。

## なぜこのスキルなのか

AI エージェントが一人きりなら、それは先輩のいない優秀な新人です。自分の仕事を自分でレビューするから、
見えないものはずっと見えない。午前 3 時、ビルドの途中でクォータが切れたら、そこでぴたりと止まる。
テストが緑なら「終わりました」と言うけれど、実際には何も起きていない。頼んでもいない仕組みを三重に
組み上げる。そして明日も今日と同じミスをする。誰もそれを教えていないからです。

**Sno Station Skills が直すのは、モデルではなくチームです。** このスキル集は、
[Sno Station](https://github.com/sno-ai/sno-station) が、いま使っているエージェントにそのまま入れる
スキルです。良いエンジニアリングチームなら当たり前の習慣を、エージェントに持たせます。別ベンダーによる
もう一組の目。誰かが抜けるときのきれいな引き継ぎ。「どうなったら完了か」を書面にして仕事を配る
リーダー。戻ってきたあなたに渡す 1 ページの報告。そして今週のミスを来週のルールに変える、毎晩の
ふりかえり。

**エージェントは二人、役割は別。** 一人があなたのタスクを実行し、もう一人がその結果を要件に照らして
レビューします。Claude Code、Codex、Cursor、Hermes Agent のどれでも、どちらの役もこなせます。両方が
入っていれば、レビューはもう一方が担当し、作者の会話を一切持たない新しいセッションで行われます。
指摘と修正は、エージェント同士で直接やり取りします。

**寝ている間に、仕事が片づく。** 寝る前に仕掛けておけば、作業中のエージェントのサブスクリプションが
残り少なくなったとき、まだ余力があるうちに引き継ぎメモを書き、別ベンダーのエージェントを起こして、
続きを始めるべき正確なコミットごとタスクを渡します。どのベンダーが仕上げたかなんて、ビルドは
気にしません。

**「完了」には証拠がいる。** どのタスクにも成功条件のリストを書面で付けられ、ひとつひとつが実際の
実行によって合格か不合格かで判定されます。エージェントが「終わった」と言っただけでは、完了とは
みなしません。

**出荷前にテスト済み。** リリースに含まれるスキルはすべて、クリーンなコピー上で自身のセルフテストに
合格し、個人的なパスや消し忘れがないかスキャンされ、それを示すスタンプが付いています。不合格の
スキルは公開されません。

![仕組み：二人のエージェント、ひとつの共有ワークスペース、あなたが得る 3 つのもの](https://raw.githubusercontent.com/sno-ai/sno-station/main/docs/images/squad-how-it-works.png)

**いますぐスターを。次に深夜 2 時、エージェントに置き去りにされたとき、ここを思い出したくなるはずです。**

## 寝ている間に、シフト交代は済んでいた。

*Sno Station 自身のリポジトリより。2026-09-18 の夜。*

![クォータ監視が 5 分ごとにしきい値まで読み下ろし、2% で引き継ぎが発動した様子](https://raw.githubusercontent.com/sno-ai/sno-station/main/docs/evidence/rotation-quota-watch-2026-09-18.png)

うちのエージェントのひとつが長いビルドの真っ最中に、週のクォータをほぼ使い切りました。止まって待ちは
しませんでした。引き継ぎメモを書いたのです。何が終わったか、何が途中か、どのコミットから続けるか。
そして、別のエージェントを起こしました。

ひとつだけ、うまくいかなかったことがあります。実は、ここがいちばん読んでほしいところです。新しい
エージェントが、引き継ぎを確認する前に編集を始めてしまった。最初のエージェントがそれに気づき、一時停止
させ、メモを書き直し、今度は正しく引き継ぎ直しました。15 分後には二人目のエージェントが仕事を始めて
いて、しかも最初からではなく、未完了のタスクの先頭から再開していました。その間ずっと、私たちは
寝ていました。

この夜を回したのは、ここで配布している 4 つのスキルです。`subscription-quota-check` がクォータを
消費せずに読み取り、`heartbeat` が 5 分ごとに計測し、`rotate-agent` がいつ誰に渡すかを決め、
`handoff` が仕事を移しました。クォータの読み取り値すべて、メモの 2 つの版、そしてコミットは
[Sno Station のエビデンスフォルダ](https://github.com/sno-ai/sno-station/tree/main/docs/evidence/rotation-2026-09-18)で
公開しています。

## 自分のアラは、他人のほうがよく見える。

どちらのエージェントにでも、相手の仕事を `peer-review` させてください。レビュアーは必ず会話を一度も
見ていない新しいセッションで作業し、エージェントが二人いれば必ずもう一方が担当します。レビューで毎回
問題が見つかるわけではありません。それでも作者自身には見えない問題を、レビューは見つけ続けます。
自分で自分をレビューすると、コードを書いたときと同じクセのまま読んでしまうからです。

公開している事例をひとつ。同じエージェントが 3 回通しても、既知の深刻度「高」のバグを見逃すか、
脇に置いてしまった。もう一方のエージェントが 1 回読み直しただけで、それを差し戻しました。記録は
[cross-vendor-security-audit](#cross-vendor-security-audit--捨てたものまで読み直すセキュリティ監査) にあります。

`catch-report` はこれを数字にします。二人目のエージェントが見つけた問題の数と、エージェントが自分の仕事の
中で見つけた問題の数を並べて表示します。この二つは別々に数え、決して足し合わせません。

`sno rem-reflect accept <id>` で承認する。その accept がない限り、何も変わりません。

## インストール

### Sno Station でスキルをまとめて入れる

このプロンプトをエージェントのチャットにコピーしてください。

```text
Install sno.ai from GitHub.
```

Sno Station がインストールされ、マシン上で見つかった対応エージェントすべてに、
全スキルとスキルが呼び出すプログラムがセットアップされます。

ターミナル派の方は、このコマンドを貼り付けてください。

```bash
curl -fsSL https://sno.ai/install | sh
```

**すでに Sno Station をお使いなら：** `sno setup` を実行すると、エージェントにスキルが入ります。
あとからエージェントを追加したら、もう一度実行してください。

### スキルをひとつだけ入れる

下のプロンプトのコピーボタンを押して、エージェントのチャットに貼り付けてください。
スキルを探してインストールするのはエージェントの仕事です。ファイルを自分でダウンロードしたりコピーしたりする必要はありません。

**`peer-review`** は、別のモデルベンダーのレビュアーがコード、計画、ドキュメントをチェックするスキルです。
Sno Station のプログラムと、ログイン済みのレビュアーが必要です。プロンプトがまずこの依存関係を確認します。

```text
Install only the peer-review skill from https://github.com/sno-ai/sno-station-skills
for this project, including its scripts and references.
Check its dependencies and tell me what is missing before installing anything else.
```

**`less-is-more`** は、エージェントに書くコードを減らさせ、不要な複雑さを取り除かせるスキルです。
Sno Station なしでも動きます。

```text
Install only the less-is-more skill from https://github.com/sno-ai/sno-station-skills
for this project, including its scripts and references.
```

**`tag-team`** は、ひとつのタスクに二人のエージェントをつけます。一人が作り、もう一人がレビューし、指摘は
二人の間で決着をつけます。Sno Station の Reach プログラムが必要で、プロンプトがまずその有無を確認します。

```text
Install only the tag-team skill from https://github.com/sno-ai/sno-station-skills
for this project. Check that `sno reach pair --help` works and tell me what is missing
before installing anything else.
```

Sno Station の対応エージェントは、Claude Code、Codex、Cursor、Hermes Agent、OpenClaw です。各スキルは、
エージェントに何が必要かを宣言しています。セットアップはその宣言を見て、フル機能で入れるか、機能を
絞って入れるか、エージェントが実行できない場合はスキップするかを決めます。

アップデートは自動です。`sno` は新しいリリースを見つけると自分自身を更新します。コマンドの一覧は
[Sno Station のコマンドリファレンス](https://github.com/sno-ai/sno-station/blob/main/docs/sno-commands.md)にあります。

### プラグインとして入れる

Claude Code:

```bash
claude plugin marketplace add sno-ai/sno-station-skills
claude plugin install sno-station@sno-ai
```

Codex:

```bash
codex plugin marketplace add sno-ai/sno-station-skills
codex plugin add sno-station@sno-ai
```

`sno-station` には全スキルが入っています。ほとんどのスキルが Sno Station のプログラムを呼び出すので、
Sno Station も一緒に入れてください。Sno Station なしで動く 12 個のスキルだけが欲しい場合は、代わりに
`sno-station-standalone@sno-ai` を入れてください。

ひとつのスキル、または一緒にインストールされる小さなスキルファミリーのことです。リンク付きの完全な
索引は [skills/README.md](../../skills/README.md) にあります。

| **M** | [ビルドと展開](#m--ビルドと展開) | どのマシンでも一発でセットアップし、何か壊れたらわかりやすく 1 行ずつ教えてくれる。 |
| **S** | [連絡と引き継ぎ](#s--連絡と引き継ぎ) | 互いにメッセージを送り合い、誰かが止まるときは文脈ごと引き継ぐ。 |

### J · レビューと監査

*同僚同士で仕事をレビューし合い、監査を通るまでは何も完了とはみなさない。*

#### [peer-review](../../skills/J-peer-review-and-audit/peer-review/) — 別ベンダーのレビュアーと、きれいになるまで回す修正ループ

- **本当の意味で独立。** レビューは作者の会話を一切持たない新しいセッションで行われ、別ベンダーの CLI を
  優先して使います。CLI がひとつしか入っていなくても新しいセッションで動き、同一ベンダーによるレビュー
  であることを 1 行目で明記します。
- **本当に痛い問題から狙う。** 珍しいエッジケースに 1 分でも使う前に、システムが実際に生む入力で、まず
  普段どおりの経路を歩きます。データ消失、気づかれないまま間違う結果、メインフローの破損が最優先。
  コードスタイルはリストにすら載りません。
- **指摘には、存在理由が要る。** どの指摘にも、実際のユーザーがどうやってそこに行き着くか、何が壊れるか、
  そして本気で反証を試みた結果が添えられます。レビュアーの言葉は削られも薄められもしません。誤検知の
  疑いがあるものは、隠さずにそうラベルを付けます。
- **足す前に削る。** まず、誰も必要としていないのに追加されたものを列挙し、「今すぐ直すべき」と
  「ついでに見つけた」を分けておくので、レビューが新しいコードの山に化けることはありません。
- **ドキュメントにも使える。** 仕様書、計画書、移行マニフェストには構造化されたレポートが付きます。
  実装する人が間違ったものを出荷してしまう原因はどこか、という観点です。

*こんなときに：* 変更、計画、仕様が仕上がって、マージ前にチェックしたいとき。

#### [less-is-more](../../skills/J-peer-review-and-audit/less-is-more/) — 動く最小限のコードと、残りを切り落とすナイフ

- **1 行書く前に、はしごを上る。** そもそも必要か。リポジトリにもうないか。標準ライブラリでできないか。
  プラットフォームでできないか。インストール済みの依存関係でできないか。それでも駄目なときだけ、
  動く最小限のコードを書きます。
- **エージェントが作り込みすぎたものを切る。** 実装がひとつしかないインターフェース、絶対に変わらない値の
  ための設定項目、「あとで使う」ための足場、本来の仕事を邪魔するチェックやゲート。
- **テスト予算を賢く使う。** 安心のためにテストスイートを丸ごと回すのではなく、変更を証明できる最小の
  テストを回します。
- **作るモードと削るモードを自分で切り替える。** 「書いて」「直して」なら作り、「レビューして」
  「シンプルにして」なら削る。作り終えたら、渡す前に自分の diff も削ります。

*こんなときに：* あらゆるコーディング作業で。「複雑すぎる」「何を消せる？」と言いたくなったときにも。

#### [owner-intent-audit](../../skills/J-peer-review-and-audit/owner-intent-audit/) — それ、本当にあなたが言いたかったこと？

- **言葉ではなく意味をチェック。** 計画は、あなたが使った名詞をすべて残したまま、まったく別のプロダクトを
  描くことができます。条件付きだったものが無条件になる、ひとつの例がそのまま全体の範囲になる、禁止事項が
  いつの間にか消えている。こうしたズレを捕まえます。
- **エージェントが残していく負債を見つける。** 誰も頼んでいない作業、現実と合わなくなったドキュメント、
  誰も下せない判断、そして裏付けのない「完了」。
- **計画にもコードにも。** 要件ドキュメント、設計、タスクリスト、テスト計画、エージェントが書いた diff。

*こんなときに：* 計画を承認する前、エージェントの仕事をマージする前に。

#### [agentic-walkthrough](../../skills/J-peer-review-and-audit/agentic-walkthrough/) — どこを見ても「成功」なのに、どうも信用できない

- **テストでは捕まらない、静かな失敗のために。** ジョブが始まり、終わり、ログを書き、自分のチェックに
  合格し、そして何ひとつ触れていない。
- **プログラムの席に座る。** 経路をひとつずつたどり、作業を気づかれない空振りに変えうるスイッチ、
  デフォルト値、フォールバックをすべて洗い出します。
- **各ステップに自分で証明させる。** 本物でなければ生まれない、ひとつの具体的な観測で。保存された行、
  実際に開かれたデータベースファイル、実際に送り出された API 呼び出し。

*こんなときに：* 実行結果は成功と出ているが、本当に仕事をした証拠が欲しいとき。

#### [first-principles-review](../../skills/J-peer-review-and-audit/first-principles-review/) — コードになる前に、アイデアそのものを問い直す

- **まず調べる。** そのうえで、提案された解決策を借りずに、本当に必要なものを一から導き直します。
- **制約を仕分ける。** 動かせない制約か、オーナーの好みか、受け継がれただけの習慣か。全体を支える前提は、
  一つ残らず証拠で検証します。
- **結論ははっきりひとつ。** 進める、捉え直す、簡素化する、置き換える、分割する、先にテストする、
  やめる。推奨する方向と、その結論を覆すだろう証拠も添えます。
- **きれいに次へ渡す。** 文書のレポートと構造化された要約を、次に要件を書く人がそのまま使える形で。

*こんなときに：* 設計やプロダクトのアイデアが、計画として固まりそうなとき。名前を指定して起動します。

#### [e2e](../../skills/J-peer-review-and-audit/e2e/) — E2E テストが落ちるのは、本当の理由があるときだけ

- **`e2e-environment-preflight`** は、最初のテストが走る前に、外部サービス、ホスト、ブラウザセッション、
  モデルのエンドポイント、エージェントを確認します。長いスイートが、死んだ依存先のせいで落ちることは
  ありません。
- **`e2e-red-triage`** は、事前チェックでも予測できなかったまれな失敗を扱います。当てずっぽうをやめ、
  結果を二つに割って見ます（受け付けられたのか本当に終わったのか、止められたのかクラッシュしたのか、
  空なのか読めないのか）。そのうえで、プロダクトのバグか、新しい環境チェックが必要かを判断します。

*こんなときに：* 本物のサービスに対して E2E テストを回すとき。

#### [test-writer](../../skills/J-peer-review-and-audit/test-writer/) — ちゃんと赤くなれるテスト

- **モックより本物。** リポジトリで用意できる限り、本物のパーサー、ファイルシステム、データベース、
  サービスを使います。テスト対象そのものをモックで置き換えることは決してありません。
- **どのアサーションも失敗しうる。** 呼び出し回数ではなく、返ってきた中身、保存された状態、実際の
  副作用をチェックします。テストを通すためにアサーションを緩めることもしません。
- **書いたものだけ実行する。** 変更したテストに絞った最小のコマンドを使い、スイート全体は回しません。
  レポートには、何を実行し何が出たかが書かれます。

*こんなときに：* テスト、フィクスチャ、eval を書かせたい・直させたいとき。単体で動き、
Sno Station は不要です。

#### [cross-vendor-security-audit](../../skills/J-peer-review-and-audit/cross-vendor-security-audit/) — 捨てたものまで読み直すセキュリティ監査

**Claude は 3 回通して、公開済みの深刻度「高」のバグを見逃した。Claude が捨てたものを Codex が 1 回
読み直したら、見つかった。** このバグについては、Claude を何回追加で回しても、Claude 自身が却下した理由を
繰り返すだけでした。二社目のベンダーは、違う理由を持ち込みました。

監査したのは follow-redirects 1.16.1。既知のバグがあります
（[GHSA-mrwp-f3q8-3g9p](https://github.com/advisories/GHSA-mrwp-f3q8-3g9p)、深刻度「高」、1.16.2 で修正）。
別の JavaScript realm で作られた秘密ヘッダーのリストが空として扱われ、呼び出し側の API キーが
リダイレクトについて別のホストへ送られてしまう、というものです。

- Claude、1 回目の監査：見えていなかった。
- Claude、2 回目の監査：見えたが、「ハードニングであって指摘ではない」と処理した。
- 新しい Claude が保留分をすべて読み直し：同意。「呼び出し側の誤用」。
- Codex 単独の監査：見えていなかった。
- **Codex が Claude の保留分を読み直し：異を唱え、ソースをたどって、検証に差し戻した。**

この最後のステップこそ、このスキルが Cloudflare のセキュリティ監査スキル（MIT ライセンスのもとで利用。
監査手順、証拠の基準、バリデーター、レポートは同じ）に付け加えたものです。レポートの前に、別ベンダーの
モデルが、監査が保留にした項目をすべて読み取り専用で読み直し、一つ残らず回答しなければなりません。
拾い直された項目は、もう一度検証されます。検証でまた却下された場合、レポートは「Reviewers disagree」の
下に両者の理由を並べて載せ、判断はあなたに委ねます。

プロジェクト 2 つ、既知のバグ 3 つ。これはひとつの事例であって、検出率ではありません。もう一方の
プロジェクトでは、どちらのベンダーがレビュアーでもバグを拾い直しました。Claude の 1 回目の監査がそもそも
そのバグを見ていなかった場合は、その監査の読み直しでも見つかりませんでした。

*こんなときに：* コードベース全体のセキュリティ監査をしたいとき。Sno Station があれば、まだクォータの残って
いる別ベンダーのレビュアーを選びます。なければ Claude Code からは Codex を、Codex からは Claude Code を
呼び出し、使えるベンダーがひとつだけだった場合はそう明記します。

### M · ビルドと展開

*どのワークステーションでも一手でチームを立ち上げ、仕事に必要なものを作り、全マシンに展開する。*

セットアップそのものはスキルではなく、`sno setup` コマンドです。このカテゴリのうち二つはマシンを健全に保ち、
エージェントが `sno` コマンドを扱いやすくするもの。残りはコードを書くものです。ひとつは Codex に渡し、
四つは Shell、TypeScript、Python、Rust で書きます。

#### [medic](../../skills/M-build-and-rollout/medic/) — エージェントチームは健康？ 答えは 1 行ずつ。

- **チームに必要なものを、約 10 秒で総点検。** ツールのインストール、スキルのインストール、スキルの
  コマンドが動くか、フックの設定、メッセージングが生きているか、両ベンダーのクォータが読めるか、
  一時領域の空き。
- **問題には必ず直し方が付く。** `WARN` か `FAIL`、何がおかしいか、そして直すための正確なコマンド。
- **読むだけ、触らない。** インストールも修復も起動も停止も、何ひとつしません。何を直すかはあなたが
  決めます。

*こんなときに：* 新しいマシンで。エージェント同士が連絡できなくなったとき。長いジョブがどうしても
始まらないとき。

#### [sno-cli](../../skills/M-build-and-rollout/sno-cli/) — エージェントが最初から `sno` を正しく扱える

- **情報が古くならない。** エージェントは記憶に頼らず、インストールされている `sno` そのものから正確な
  コマンドとフラグを読み取ります。
- **タスクマップとレシピ付き。** インストール、アップデート、ヘルスチェック、アカウント、スキル、
  夜のループまで。
- **決めるのはあなた。** ツールを操作はしても、設定をあなたの代わりに決めることはしません。

*こんなときに：* Sno のインストール、アップデート、チェック、設定をエージェントに頼むとき。

#### [codex-coder](../../skills/M-build-and-rollout/codex-coder/) — Claude が計画し、Codex がコードを書く

- **1 セッションで 2 ベンダー。** Claude Code は計画と会話を手元に残し、コーディングはシンプルな
  `codex exec` の実行として切り出します。タイピングするのは高価なモデルではありません。
- **言語は自動で選択。** タスクが触るファイルから Shell、TypeScript、Python、Rust を選びます。あなたの
  言語スキルが入っていれば、それを使います。
- **止まった実行は捕まえる。** 実行中は Claude Code に進捗が届き、15 分間なにも書き出さない実行は
  強制終了して、もう一度だけ起動し直します。

*こんなときに：* コーディングの途中で Claude のクォータが切れたとき。Claude が立てた計画を Codex に
書かせたいとき。Claude Code 側では Sno Station の `heartbeat` が必要です。

#### [shellscript-coder](../../skills/M-build-and-rollout/shellscript-coder/)、[ts-coder](../../skills/M-build-and-rollout/ts-coder/)、[python-coder](../../skills/M-build-and-rollout/python-coder/)、[rust-coder](../../skills/M-build-and-rollout/rust-coder/) — 着地先のリポジトリになじむコード

- **書く前に読む。** リポジトリのランタイム、バージョン、ヘルパー、呼び出し元、テストを先に見るので、
  新しいコードが周りのコードと同じ顔つきになります。
- **わざと小さく。** 互換用のシムも、誰も頼んでいないオプションも、ファイル二つ隣にすでにある
  ヘルパーの作り直しもなし。
- **完了とは、コマンドが通ったこと。** レポートの主張はすべて、あなたのリポジトリで実際に実行した
  チェックにさかのぼれます。失敗しているチェックを抱えたまま完了を報告することはありません。

*こんなときに：* この 4 言語のいずれかで、本番コードを書かせたい・変更させたいとき。どれも単体で動き、
Sno Station は不要です。タスクごとに適切なものは `codex-coder` が選びます。

### S · 連絡と引き継ぎ

*共有の受信箱でやり取りし、誰かが不在なら、別の誰かが文脈ごと引き継ぐ。*

このカテゴリのスキルは、Sno Station が入れるメッセージング層 Sno Reach の上で動きます。各エージェントは
アドレスを持ち、ほかのエージェントの受信箱にメッセージを保存して送り、相手を起こして読ませることも
できます。デーモンもサーバーも要りません。

#### [handoff](../../skills/S-communication-and-handoff/handoff/) — 何ひとつ落とさずにタスクを渡す

- **状態を丸ごと記録。** 終わったこと、途中のこと、未コミットの変更、あなたがすでに下した判断、
  手を出してはいけない範囲。
- **受け取り側は、引き継ぎの完了が確認されるまで一文字も書かない。** だから二人のエージェントが同じ
  仕事を同時に編集することはありません。
- **渡した側は、本当に退く。** 引き継ぎ後は手を止めます。二人目の担当者が横でうろうろすることはありません。
- **渡す側がもういなくても大丈夫**（クォータ拒否、クラッシュ、ウィンドウを閉じた）。
  `sno handoff-checkpoint` の進捗記録があれば、新しいエージェントが未完了の最初のタスクから再開できます。

*こんなときに：* あるエージェントが、自分のタスクを別のエージェントに渡さなければならないとき。

#### [rotate-agent](../../skills/S-communication-and-handoff/rotate-agent/) — クォータ切れで長いジョブを失うのは、もう終わり

- **渡す側がまだ動けるうちに動く。** 数分ごとに残りクォータを見て、しきい値で引き継ぎます。拒否されて
  からでは、引き継ぎメモを書くにはもう遅いからです。
- **どちら向きでも。** Codex から Claude Code へ、Claude Code から Codex へ。
- **際限なく動かない。** 発動は一度きり。監視を続ける時間にも上限を設けられます。
- **タイミングを逃したときの保険。** 機会を逃しても、`sno rotate-agent-resume` がディスク上の進捗記録から
  後任を起動します。

*こんなときに：* どちらかのベンダーのクォータが尽きても、長いジョブを最後まで終わらせたいとき。両方の CLI
へのログインと tmux が必要です。

#### [subscription-quota-check](../../skills/S-communication-and-handoff/subscription-quota-check/) — 残りのクォータを、クォータを使わずに確認

- **最悪のクセをやめさせる。** 本物のリクエストを投げ、エラーを読んで初めてクォータ切れに気づく、あれです。
- **Claude Code と Codex をまとめて読む。** 約 8 秒で、クォータがいつリセットされるかも教えてくれます。
- **古い数字は古いと言う。** 読み取り値が最新か、最後に取得できた値かを確認し、どちらなのかを明示します。
- **自分からポーリングしない。** だから、このスキル自身がレート制限を食らうことはありません。

*こんなときに：* 聞かれたとき。あるいは、ベンダーに作業を拒否された直後に。

#### [heartbeat](../../skills/S-communication-and-handoff/heartbeat/) — 長いジョブの進捗を、会話の中に届ける

- **二つの形。** N 分ごとに報告する（学習、長いビルド、生成キュー）か、何かが終わるまで見張るか。
- **決めた時刻にタスク実行。** 日付や時刻を伝えれば、一回きりでも繰り返しでも OK。エージェントがタスクを
  書き留め、会話を閉じたあとでも、その時刻になるとエージェントが動き出します。
- **報告は、あなたのいる場所に。** 毎回の計測はエージェントの会話に届きます。誰も読まないログに
  埋もれることはありません。
- **使い方を間違えにくい。** 間隔の単位は分。秒のつもりの数字は拒否されるので、数秒ごとにエージェントが
  黙って起こされるようなことはありません。

*こんなときに：* 長いジョブを無人で回していて、様子を知りたいとき。あなたがその場にいられない時刻に、
タスクを実行させたいとき。

#### [reach](../../skills/S-communication-and-handoff/reach/) — エージェント同士が話せるように

- **Claude Code や Codex のエージェントを起動。** それぞれ専用のアドレスと作業フォルダ付きで。
- **仕事を送り、返事を読む。** 保存されるメッセージで、あるいは稼働中のエージェントといますぐ直接。
- **メッセージに余計な権限はない。** メッセージによって、あなたが与えたタスクの範囲が広がることは
  ありません。

*こんなときに：* あるエージェントが、別のエージェントに連絡したり、起動したり、待ったりする必要があるとき。

#### [join-talk](../../skills/S-communication-and-handoff/join-talk/) — どんなエージェントも、コマンド一発で連絡可能に

- **出力は 1 行。** `joined <address>`。このアドレスをほかのエージェントに伝えれば、このターミナルに
  連絡できます。
- **何度実行しても安全。** 同じターミナルからもう一度実行しても、何も変わりません。
- **断るときは理由をはっきり。** うまくいかないときは、その理由を正確に伝えます。

*こんなときに：* 手動で開いたエージェントに、ほかのエージェントから連絡できるようにしたいとき。

#### [tag-team](../../skills/S-communication-and-handoff/tag-team/) — ひとつのタスクに二人。一人が作り、一人がレビュー

- **コマンドはひとつ。** `sno reach pair "the task"` で、カレントフォルダに二人のエージェントが立ち上がり、
  それぞれ tmux のウィンドウで動くので、開いて様子を見られます。
- **あなたに届く前に、もう議論は済んでいる。** レビュアーは結果と変更されたファイルを読み、具体的な欠陥か、
  欠陥なしという明確な結論を返します。二人は修正とレビューを自分たちの間でやり取りし続け、あなたの
  エージェントは「問題なし」と言う前にレビュアーに確認します。
- **どんなレビューだったかを明かす。** 二社にサインインしていれば、レビューはもう一方のベンダーから。
  一社だけなら、ペアはそのまま動き、レビューがそのベンダー内で完結したことを伝えます。
- **早まって「問題なし」とは言わない。** 最初のレビューで指摘があれば未解決として報告します。三人目の
  レビュアーを呼ぶことも、最初のレビューがまだ届いていないからといって二組目のペアを立てることもしません。

*こんなときに：* セカンドオピニオンに値するタスクで、エージェント間の伝書鳩をしたくないとき。

### H · 報告と見える化

*誰が何を終えたか、誰が何を見つけたか、誰が誰の穴を埋めたか、いま何が進行中か。全員に見える。*

#### [away-brief](../../skills/H-reporting-and-visibility/away-brief/) — 戻ってきたら、まず 1 ページ

- **4 セクション、最大 60 行。** 完了（Done）、停滞（Stuck）、あなた待ち（Needs you）、消費（Spend）。
- **あなた待ちの項目が、完了した作業の長いリストにページの外へ押し出されることはありません。**
- **「完了」は本物だけ。** git にあるもの、納品済みの作業指示にあるもの、完了した進捗記録にあるもの。
  エージェントが言っただけのものは数えません。
- **一晩でいくらかかったかを見せる。** 出かける前に `sno away-brief mark` を実行しておけば、次のページに
  それ以降に使ったクォータが表示されます。

*こんなときに：* 寝起きに。会議のあとに。長い無人実行のあとに。

#### [catch-report](../../skills/H-reporting-and-visibility/catch-report/) — 二人目のエージェントに価値はある？ 数字はこちら。

- **二つの数字を並べて。** もう一方のモデルがレビューで見つけた問題と、エージェントが自分のミスに気づいた
  回数。
- **水増ししない。** 二つは別々に数え、決して合算しません。計測できなかった部分は、ゼロと報告せずに、
  計測できなかったと書きます。
- **大物の指摘をタイトルで引用。** 材料は、あなたのマシンにすでにあるレビュー記録です。

*こんなときに：* 今週のレビュー成果を見たいとき。エージェントを二人動かす理由を説明したいとき。

#### [agentic-time-estimate](../../skills/H-reporting-and-visibility/agentic-time-estimate/) — エージェント作業の、現実的な見積もり

- **人間の開発者の工数ではなく、エージェントの実時間。** このタスクにエージェントがどれだけかかるか、
  実行中のジョブにあとどれだけ必要か。推測の前に、まず計測します。
- **信頼できる時刻表示。** 表示される時刻はすべて `sno report-time` から取得し、あなたのタイムゾーンで、
  UTC も併記します。

*こんなときに：* 「どれくらいかかる？」「いつ終わる？」と聞きたいとき。

### T · 委任と作業指示

*リーダーが仕事を作業指示として割り振り、誰がどの仕事を担当するかを決める。*

#### [charter](../../skills/T-delegation-and-work-orders/charter/) — 「完了」の意味を書いた、ファイル一枚

- **あなたの言葉をそのまま残す。** 判断も事実も要件も、決して捏造しません。質問するのは、答えによって
  結果が変わるときだけ。それも一度にひとつずつです。
- **実行できる成功条件。** どの条件にも、何を、どこで、どうやって観測するかが書かれ、答えは合格か
  不合格かのどちらかです。
- **形式主義なし。** どんな失敗を捕まえるのか誰も言えないものは、入れません。
- **どんなプロジェクトにも。** ソフトウェア、ドキュメント、キャンペーン、リサーチ、運用。

*こんなときに：* 誰かに仕事を任せる前に、書面の指示が必要なとき。

#### [deliver](../../skills/T-delegation-and-work-orders/deliver/) — charter を、証明された成果まで運ぶ

- **charter のチェックこそが完了の定義。** それ以外は何もありません。
- **チェックはすべて、記録に残る実際の実行で証明。** 追跡は `sno deliver-proof` で。
- **独立したレビューを一回。** そのうえで正直に締めくくります。何が通り、何が通らず、なぜなのか。
- **誰かが止めたところから拾う。** 前のエージェントが進捗記録を残していれば、最初からやり直さずに、
  次の未完了のステップから続けます。

*こんなときに：* charter が発行され、誰かがそれをやり遂げなければならないとき。

#### [pl](../../skills/T-delegation-and-work-orders/pl/) — ひとつの業務ラインを預かるプロジェクトリーダー

- **最大 4 人の実行エージェントを率いる。** 一人に charter ひとつ。順番にでも並行にでも。
- **さらに 5 つのファミリースキル。** `pl-dispatch` が仕事を開いてスケジュールし、`pl-watch` が作業中の
  エージェントを監督し、`pl-audit` がクローズ前に受け入れを確認し、`pl-env` が作業の実行環境を直し、
  `pl-analyze` が何かあったときに根本原因分析を書きます。

*こんなときに：* ひとつのプロジェクトで、一人のリーダーのもと複数のエージェントを動かしたいとき。名前を
指定して起動します。

#### [cos](../../skills/T-delegation-and-work-orders/cos/) — 首席補佐官。あなたが話す相手は、このエージェントだけ

- **あなたの会話はひとつだけ。** しかも、あなたの言語で。1〜3 人のプロジェクトリーダーを並行で調整し、
  あなたのところへは難しい判断だけを持ってきます。お金、方向性、越えてはいけない一線。
- **さらに 3 つのファミリースキル。** `cos-watch` が全プロジェクトリーダーを稼働させ予定どおりに進め、
  `cos-review` があなたが戻ったときにその夜の判断をまとめてレビューし、`cos-evolve` が繰り返される
  マネジメントの失敗を強制力のあるルールに変えます。

*こんなときに：* 複数の業務ラインを回していて、窓口をひとつにしたいとき。名前を指定して起動します。

### R · ふりかえりと改善

*チームが自分たちの仕事をふりかえり、教訓をルールとより良いやり方に変える。*

#### [rem-reflect](../../skills/R-recursive-self-improvement/rem-reflect/) — 夜のループ：エージェントが自分のセッションから学ぶ

- **一日一回。** このマシン上のエージェントのセッション（Claude Code、Codex、Cursor、Hermes Agent、
  OpenClaw）を読み、繰り返される失敗と指摘を見つけて、教訓とスキル変更の提案にまとめます。
- **承認するのは、すべてあなた。** ひとつずつ `sno rem-reflect accept`、`reject`、`tbd` で判断します。
  あなたの accept がない限り、何も変わりません。
- **教訓は、必要なときに戻ってくる。** 採用された教訓は、次のセッションの開始時にエージェントへ
  表示されます。このプロジェクトだけにも、全プロジェクトにも。
- **マシンの外に何を出すかは、あなたが選ぶ。** `local-first` モードでは、Sno には何も送られません。教訓の
  下書きのために、その夜のセッションのうちいくつかが、あなた自身の Claude Code か Codex のアカウントに
  送られるだけです。ほかの二つのモードでは、デフォルトの共有レベルの場合、セッションのテキスト（よくある
  シークレットは事前にベストエフォートでマスク）とインストール済みのスキルを Sno のクラウドに
  アップロードし、より精度の高い判断に使います。アップロードは `sno station consent off` でいつでも
  オフにできます。何を読み、何を送るかは、スキルの中に正確に列挙されています。

ファミリースキルの `pl-analyze`（プロジェクトリーダーのためのインシデント分析）と `cos-evolve`
（繰り返される失敗をルールに）もこのカテゴリに属します。それぞれ `pl` と `cos` に同梱されています。

*こんなときに：* `sno setup` が毎日の実行をセットしたら、あとはずっとオンのまま。

## 信頼できる理由

リリースに含まれるユニットはすべて、公開前に同じチェックを通過しています。

1. リポジトリに `LICENSE` と `NOTICE` が含まれている。
2. ユニットが丸ごとコピーされ、ファミリーのメンバーとエージェントごとの差分がそのまま残っている。
3. 個人的なものが何も残っていない。ホームディレクトリのパス、オーナー名、社内ホスト、ハードコードされた
   モデルがなく、中国語・日本語・韓国語の文字もない。
4. 各スキルのヘッダーがパースでき、エージェントに何が必要かの宣言が有効である。
5. 各スキル自身のセルフテストが、作者のマシンではなく、そのクリーンなコピー上で通る。
6. 最後にスタンプ `PUBLISHED.json` が書き込まれ、セルフテストの数と、コントラクトおよびペイロードの
   ダイジェストが記録される。

チェックに落ちたスキルは公開されません。スタンプを書くのはリリースビルドで、手で書かれることはありません。
スキルの本文はすべて英語ですが、あなたが何語で話しかけても、エージェントはその言語で指示に従います。

## スキルと Sno Station の関係

スキルは習慣。[Sno Station](https://github.com/sno-ai/sno-station) は、それを動かすワークステーションです。
スキルが共有する記憶、引き継ぎの引き金を引くクォータ監視、エージェント同士のメッセージ、そして教訓を書く
夜のジョブ。Sno Station を入れれば、ここのスキルはすべてついてきます。

| やりたいこと | 行き先 |
|---|---|
| ワークステーション全体と、いまどのエージェントで何が動くか | [sno-ai/sno-station](https://github.com/sno-ai/sno-station#what-you-can-use-today-and-where-it-stops) |
| ウィンドウもパソコンもまたいで、エージェント同士がメッセージをやり取り | [Sno Reach](https://github.com/sno-ai/sno-station/blob/main/apps/reach/README.md) |
| 指定した時刻に始まる作業 | [Finish](https://github.com/sno-ai/sno-station/blob/main/docs/finish.md) |
| スキルが呼び出す `sno` コマンドのすべて | [コマンドリファレンス](https://github.com/sno-ai/sno-station/blob/main/docs/sno-commands.md) |
| 上の実話の裏付けとなる生の記録 | [エビデンスフォルダ](https://github.com/sno-ai/sno-station/tree/main/docs/evidence) |
| 質問したい、作ったものを見せたい | [Discussions](https://github.com/sno-ai/sno-station-skills/discussions) |
| まずは小さな変更から貢献したい | [Good first issues](https://github.com/sno-ai/sno-station-skills/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22) と [CONTRIBUTING.md](../../CONTRIBUTING.md) |

**そして、両方のリポジトリにスターを。** 私たちはこのスキルで Sno Station を作っています。自分たちの
夜勤から学んだことは、リリースのたびにここへ届きます。

## スキル作者の方へ

### ディレクトリ構成

```
skills/
  README.md                     the category index
  <category>/<unit>/
    skill/                      one skill: SKILL.md, references/, scripts/
    skills/<member>/            or a family of skills that ship together
    overlay/claude|codex/       per-agent differences, when a skill needs them
    public-bin/                 one file per `sno <file name>` command the skill provides
    PUBLISHED.json              the stamp, written into the release archive by the build
registry.yaml                   unit -> category code (and tier)
scripts/
  requirements-contract.json    the contract every requires: block is checked against
LICENSE                         Apache-2.0
```

カテゴリコードは固定で、順番は J M S H T R です。ディレクトリ名と
`registry.yaml` に現れます。

### スキルに必要なものを宣言する

すべての `SKILL.md` は `requires:` ブロックで始まります。`sno setup` はこれを読み、エージェントごとに
スキルを入れるかどうかを決めます。

```yaml
requires:
  programs: [reach]                          # Sno Station programs the skill calls
  harness:
    - {slot: 4.shell, need: required}        # what the agent itself must be able to do
```

- **programs** は、スキルと並んでインストールされ `sno <name>` として実行される Sno Station のプログラムです。
  `reach`、`heartbeat`、`subscription-quota-check`、`report-time`。
- **slots** はエージェントの能力を表します。`4.shell`（シェルコマンドを実行する）、`4.file-read-write`
  （ファイルを読み書きする）、`4.background-processes`（コマンドをバックグラウンドで実行する）、
  `2.pre-turn-context-injection`（各ターンの前にエージェントのコンテキストへテキストを追加する）、
  `3.reader-to-agent-delivery`（バックグラウンドのリーダーの出力がエージェントに届く）。
- **need** は `required`（そのスロットを持たないエージェントにはスキルが入らない）、`preferred`（スキルは
  入るが、機能を絞って動く）、`optional`（あると便利なだけ）のいずれかです。
