**AI 에이전트는 머리 좋은 신입입니다. 문제는 사수가 없다는 것. 이 스킬들은 그 신입에게, 출시를 여러 번 겪어 본 팀의 일 습관을 심어 줍니다.** 만드는 에이전트와 리뷰하는 에이전트가 따로 있습니다. 사용량 한도가 바닥나기 전에 인수인계서를 쓰고, 다른 에이전트가 정확히 그 커밋에서 이어받습니다. 실제로 돌려 본 증거 없이는 누구도 "다 했어요"라고 말할 수 없습니다. 그리고 매일 밤 하루를 돌아보고 새 규칙을 제안합니다. 채택할지는 여러분이 정합니다.

**Claude Code, Codex, Cursor, Hermes Agent**에서 돌아가고, OpenClaw도 됩니다. 에이전트가 실행할 수 있는 스킬은 온전히, 실행할 수 없는 스킬은 기능을 줄인 형태로 설치됩니다.

모든 스킬은 그냥 텍스트입니다. 읽고, 복사하고, 고쳐 쓰면 됩니다. [Sno Station](https://github.com/sno-ai/sno-station)이 여러분이 이미 쓰는 에이전트에 깔아 주는 스킬이 바로 이것이고, 저희가 Sno Station을 만들면서 매일 쓰는 스킬도 바로 이것입니다.

스킬을 전부 받으려면 에이전트에게 이렇게 말하세요.

```text
install sno.ai from GitHub
```

에이전트가 Sno Station을 설치하고, 컴퓨터에서 찾은 지원 에이전트마다 모든 스킬과 스킬이 호출하는 프로그램까지 세팅합니다. 그다음 하나 써 보세요.

```text
peer-review this
```

다른 에이전트가 대화를 한 줄도 본 적 없는 새 세션에서 여러분의 변경을 읽고, 실제로 쓰면 어디가 깨지는지 알려 줍니다. [스킬 하나만, 혹은 플러그인으로 받고 싶다면?](#설치)

**처음 오셨나요?** 이 스킬들은 그림의 절반입니다. 나머지 절반은 스킬이 돌아가는 워크스테이션, [Sno Station](https://github.com/sno-ai/sno-station)입니다. 에이전트끼리 [메시지를 주고받고](https://github.com/sno-ai/sno-station/blob/main/apps/reach/README.md), [정한 시각에 일이 시작되고](https://github.com/sno-ai/sno-station/blob/main/docs/finish.md), 모두가 하나의 메모리를 같이 씁니다.

## 뭐가 달라지나

일하는 방식은 그대로입니다. 좋아하는 에이전트를 그대로 쓰세요. 달라지는 건 이런 순간들입니다.

1. **변경을 끝냈고, 검토를 받고 싶다.** "peer-review this"라고 말하세요. 다른 벤더의
   리뷰어가 아무 맥락 없이 읽고 실제로 쓰면 어디가 깨지는지 보고합니다. 작성자는 근본
   원인을 고치고, 리뷰가 깨끗하게 나올 때까지 이 왕복이 계속됩니다.
2. **자기 전에 긴 작업을 걸어 둔다.** "arm rotate-agent"라고 말하세요. 밤사이 작업 중인
   에이전트의 사용량이 기준선까지 떨어지면, 다른 벤더의 새 에이전트에게 일을 넘깁니다.
   파일 하나 건드리기 전에 인수인계서부터 확인한 다음에요.
3. **정한 시각에 처리되길 원한다.** 시각만 말하면 됩니다. "내일 9시에 빌드 확인해 줘",
   "매일 아침 7시에 리포트 써 줘". 그 시각에 에이전트가 시작해서 처리합니다. 대화창이 열려
   있든 닫혀 있든요. 예약된 일은 `sno heartbeat --due`로 봅니다. Sno Station에서 이 부분의
   이름은 Finish이고, 자세한 내용은 [가이드](https://github.com/sno-ai/sno-station/blob/main/docs/finish.md)에 있습니다.
4. **돌아왔다.** "away brief"라고 말하세요. 최대 60줄짜리 한 페이지. 끝난 일, 막힌 일과
   그 이유, 여러분의 답을 기다리는 일, 그리고 사용량을 얼마나 썼는지.
5. **남에게 맡길 일이 있다.** "write a charter"라고 말하세요. 파일 하나가 나옵니다. 무엇을
   내놓아야 하는지, 어디까지가 금지선인지, 이미 정해 둔 것은 무엇인지, 성공 기준 하나하나를
   어떻게 증명할지. 이제 어떤 에이전트든 그걸 `deliver`할 수 있고, 모든 기준은 기록이 남는
   실제 실행으로 증명됩니다.
6. **매일 밤, 팀이 회고한다.** 야간 루프가 그날 모든 에이전트의 세션을 읽고, 되풀이되는
   실수를 찾아 교훈과 스킬 수정을 제안합니다. 아침에 마음에 드는 것만
   `sno rem-reflect accept <id>`로 받아들이세요. 그 accept 없이는 아무것도 바뀌지 않습니다.

## 왜 이 스킬인가

AI 에이전트 하나는 사수 없는 똑똑한 신입입니다. 자기 코드를 자기가 리뷰하니, 자기 눈에 안
보이는 건 끝까지 못 봅니다. 새벽 3시, 빌드가 절반쯤 왔을 때 사용량이 떨어지면 그대로 멈춥니다.
테스트가 초록불이면 "다 했습니다"라고 하는데, 정작 아무 일도 일어나지 않았습니다. 시키지도 않은
장치를 세 겹씩 쌓아 올립니다. 그리고 내일도 오늘과 똑같은 실수를 합니다. 아무도 알려 주지
않았으니까요.

**Sno Station Skills는 모델이 아니라 팀을 고칩니다.** 이 스킬들은
[Sno Station](https://github.com/sno-ai/sno-station)이 여러분이 이미 쓰는 에이전트에 깔아
주는 것들입니다. 잘 굴러가는 개발팀이라면 다 가진 습관을 에이전트에게 붙여 줍니다. 다른
벤더의 두 번째 눈, 누가 자리를 비울 때의 깔끔한 인수인계, 완료 기준을 글로 적어 일을 나눠 주는
리드, 돌아왔을 때 받는 한 페이지 브리핑, 그리고 이번 주 실수를 다음 주 규칙으로 바꾸는 매일 밤의
회고.

**에이전트 둘, 역할은 따로.** 한 에이전트는 일을 하고, 다른 에이전트는 그 결과를 여러분의
요구사항에 비춰 검토합니다. Claude Code, Codex, Cursor, Hermes Agent 중 어느 쪽이든 어느 역할이든
맡을 수 있습니다. 둘 다 깔려 있으면 리뷰는 반대편에서, 작성자의 대화가 하나도 없는 새 세션에서
돌아갑니다. 지적과 수정은 에이전트끼리 주고받습니다.

**자는 동안 끝나는 일.** 자기 전에 걸어 두면, 작업 중인 에이전트의 구독 사용량이 바닥을 보일 때
아직 여력이 있을 때 인수인계서를 쓰고, 다른 벤더의 에이전트를 깨워, 이어서 할 정확한 커밋과
함께 일을 넘깁니다. 빌드 입장에선 누가 마무리했든 상관없습니다.

**"다 했다"는 증명된 것만.** 모든 작업에 성공 기준 목록을 글로 붙일 수 있고, 기준마다 실제
실행으로 통과/실패가 갈립니다. 에이전트가 다 했다고 말했다는 이유로 끝난 일은 없습니다.

**내보내기 전에 테스트합니다.** 릴리스에 들어가는 스킬은 모두 깨끗한 사본에서 자체 테스트를
통과했고, 개인 경로나 찌꺼기가 남지 않았는지 검사받았으며, 그 사실을 적은 도장을 달고 나갑니다.
떨어진 스킬은 공개되지 않습니다.

![작동 방식: 에이전트 둘, 공유 작업 공간 하나, 여러분이 얻는 세 가지](https://raw.githubusercontent.com/sno-ai/sno-station/main/docs/images/squad-how-it-works.png)

**지금 스타를 눌러 두세요. 새벽 2시에 에이전트가 멈춰 섰을 때, 이게 어디 있었는지 찾게 될 겁니다.**

## 그 짜증, 이렇게 끝냅니다

*최종 업데이트 2026-10-23.* 왼쪽 칸은 전부 2026년 10월 20일 주간에 r/ClaudeCode, r/codex, r/ClaudeAI에 실제로 올라온 불만입니다. 오른쪽 칸은 그걸 멈추려고 저희 머신에서 실제로 돌리는 것들입니다. 무료이고, 오픈소스입니다.

| 이번 주에 들린 말 | 이렇게 고칩니다 | 어디서 |
|---|---|---|
| "5시간 한도를 30분 만에 다 썼어요." | 제일 큰 모델한테 모든 걸 시키지 마세요. Opus는 계획과 리뷰를, Codex는 코드를 씁니다. 같은 세션에서 에이전트로 불러서요. 구독 하나가 바닥나면, 다른 쪽이 같은 메모리에서 일을 이어받습니다. | `codex-coder`, `sno reach call` |
| "'이 모델은 현재 용량이 가득 찼습니다' 한 줄에 밤새 돌린 10시간이 날아갔어요." | 사용량이 2% 남으면 작업 중인 에이전트가 인수인계서를 쓰고 다른 벤더의 에이전트를 깨웁니다. 그 에이전트가 정확히 그 커밋에서 이어 갑니다. 여러분은 자고 있었고요. | `rotate-agent` |
| "파일 1,100개, 3만 줄. 그 PR들 리뷰할 토큰이 없어요." | 푸시하는 사람이 먼저 리뷰합니다. 작성자가 다른 벤더에게, 대화를 본 적 없는 새 세션에서 리뷰를 돌리고, 다른 누가 보기 전에 돌아온 지적부터 고칩니다. | `peer-review` |
| "리뷰어 서브에이전트가 2주 동안 커밋마다 검사했어요. 86번 돌려서 막은 건 딱 한 번." | 하네스가 자기 자신을 리뷰하면 진짜 문제는 안 나옵니다. 리뷰어는 언제나 다른 하네스의 다른 모델이고, 작성자의 대화는 한 줄도 모릅니다. | `peer-review` |
| "Codex는 리뷰를 끝낼 줄을 몰라요." | 스킬에 상한을 박아 뒀습니다. 코드는 3라운드, 계획은 5라운드, 테스트는 1라운드. 그다음엔 멈추고 사람을 기다립니다. 15분 동안 아무것도 쓰지 않은 실행은 멈춘 걸로 보고 종료합니다. | `peer-review`, `codex-coder`, `heartbeat` |
| "Codex는 바이트 하나하나를 범죄자 취급해요." | 혹시 몰라 넣은 안전장치, 차단기, 해시는 리뷰가 제일 먼저 지웁니다. 실제로 관찰된 실패가 요구하지 않는 한 아무것도 들어가지 않습니다. | `less-is-more` |
| "Claude가 이건 안 바꾸겠다고 할 때, 그 이유가 다음에 Codex가 읽는 어딘가에 남긴 하나요?" | 모든 지적은 한 번만 기록되고, 상태는 사람만 바꿀 수 있습니다. 같은 지적이 또 나오면 새 항목이 아니라 기존 행이 갱신되고, 앞선 판정은 다음 리뷰에 넘겨집니다. | `peer-review` 지적 장부 |
| "다 했다면서요. 아무 일도 안 일어났는데." | 작업에는 성공 기준 목록이 글로 붙고, 기준마다 실제 실행으로 통과/실패가 갈립니다. 에이전트의 "다 했어요"는 아무 의미가 없습니다. | `pl` 작업 지시서 |

| "서브에이전트 절반은 컨텍스트 창만 새로 받은 한 줄짜리 명령이었어요." | 절차는 서브에이전트가 아니라 스킬에 둡니다. 에이전트는 둘만 남깁니다. 계획과 실행, 그리고 리뷰. 값을 하는 분업은 이 두 가지뿐이니까요. | 스킬 전체 |

오른쪽 칸의 스킬은 전부 이 저장소에 있고, 여러분의 에이전트에 공짜로 복사해 쓸 수 있습니다. 스킬들이 같이 쓰는 메모리, 인수인계를 터뜨리는 사용량 감시, 교훈을 써 내는 야간 실행은 [Sno Station](https://github.com/sno-ai/sno-station)에 있습니다. Sno Station을 설치하면 여기 있는 스킬도 전부 같이 들어오니, 한 번에 전부를 경험할 수 있습니다.

## 나는 잤다. 에이전트들은 교대했다.

*Sno Station 저장소에서 실제로 있었던 일, 2026-09-18 밤.*

![사용량 감시가 5분마다 기준선을 향해 내려가는 수치를 읽고, 2%에서 인수인계가 시작되는 장면](https://raw.githubusercontent.com/sno-ai/sno-station/main/docs/evidence/rotation-quota-watch-2026-09-18.png)

에이전트 하나가 긴 빌드 한가운데 있었는데, 주간 사용량이 거의 바닥났습니다. 멈춰서 기다리지
않았습니다. 인수인계서를 썼습니다. 끝낸 것, 하다 만 것, 이어서 할 정확한 커밋. 그리고 다른
에이전트를 깨웠습니다.

딱 한 가지가 꼬였고, 사실 그게 제일 읽을 만한 대목입니다. 새 에이전트가 인수인계를 확인하기도
전에 파일부터 고치기 시작한 겁니다. 첫 에이전트가 그걸 잡아내 멈추게 하고, 인수인계서를 다시
써서 이번엔 제대로 넘겼습니다. 15분쯤 뒤 두 번째 에이전트가 일하고 있었고, 처음부터가 아니라
첫 번째 미완료 작업부터 이어받았습니다. 이 모든 일이 저희가 자는 동안 벌어졌습니다.

그날 밤을 돌린 건 여기서 배포하는 스킬 네 개입니다. `subscription-quota-check`는 사용량을
축내지 않고 읽었고, `heartbeat`는 5분마다 수치를 쟀고, `rotate-agent`는 언제 누구에게 넘길지
정했고, `handoff`가 일을 옮겼습니다. 사용량 기록 전부, 인수인계서 두 버전, 커밋까지
[Sno Station의 증거 폴더](https://github.com/sno-ai/sno-station/tree/main/docs/evidence/rotation-2026-09-18)에
공개해 두었습니다.

## 등잔 밑은 옆 사람이 비춘다.

어느 에이전트에게든 상대의 작업을 `peer-review`하라고 시키세요. 리뷰어는 언제나 대화를 본 적
없는 새 세션에서 일하고, 에이전트가 둘이면 반드시 다른 쪽이 맡습니다. 리뷰가 매번 문제를 찾는
건 아닙니다. 다만 작성자가 볼 수 없던 문제를 꾸준히 찾아냅니다. 자기를 리뷰하는 에이전트는
코드를 쓸 때와 똑같은 버릇을 리뷰에도 들고 오기 때문입니다.

공개한 사례 하나. 한 에이전트가 세 번을 훑으면서 이미 알려진 고위험 버그를 놓치거나 제쳐
두었는데, 다른 에이전트가 한 번 다시 읽고 그걸 되돌려 보냈습니다. 기록은
[cross-vendor-security-audit](#cross-vendor-security-audit--버린-것을-다시-읽는-보안-감사)에 있습니다.

`catch-report`는 이걸 숫자로 보여 줍니다. 두 번째 에이전트가 잡은 문제 수, 그리고 에이전트들이
자기 작업에서 스스로 잡은 문제 수. 둘은 따로 세고, 절대 합치지 않습니다.

## 어젯밤 에이전트한테 버럭했다. 녀석은 받아 적었다.

실수를 찾아, 에이전트 자신의 스킬을 고치자고 제안합니다. 아침에 원하는 것만

## 설치

### Sno Station으로 스킬 전부 설치

이 프롬프트를 에이전트 채팅창에 붙여 넣으세요.

```text
Install sno.ai from GitHub.
```

Sno Station이 설치되고, 머신에서 찾은 지원 에이전트마다 모든 스킬과 스킬이 호출하는 프로그램이
세팅됩니다.

아니면 이 명령을 터미널에 붙여 넣으세요.

```bash
curl -fsSL https://sno.ai/install | sh
```

**이미 Sno Station이 있다면?** `sno setup`을 실행하면 에이전트에 스킬이 설치됩니다. 나중에
에이전트를 하나 더 들이면 한 번 더 실행하세요.

### 스킬 하나만 설치

아래 프롬프트 중 하나를 복사 버튼으로 복사해 에이전트 채팅창에 붙여 넣으세요. 에이전트가 스킬을
찾아서 설치합니다. 파일을 직접 내려받거나 복사할 필요는 없습니다.

**`peer-review`** 스킬은 다른 모델 벤더의 리뷰어로 코드, 계획, 문서를 검토합니다. Sno Station
프로그램과 로그인된 리뷰어가 필요합니다. 프롬프트가 이 의존성부터 확인합니다.

```text
Install only the peer-review skill from https://github.com/sno-ai/sno-station-skills
for this project, including its scripts and references.
Check its dependencies and tell me what is missing before installing anything else.
```

**`less-is-more`** 스킬은 에이전트가 코드를 덜 쓰고 쓸데없는 복잡도를 걷어 내게 돕습니다. Sno Station
없이도 돌아갑니다.

```text
Install only the less-is-more skill from https://github.com/sno-ai/sno-station-skills
for this project, including its scripts and references.
```

**`tag-team`** 스킬은 한 작업에 에이전트 둘을 붙입니다. 하나는 만들고 하나는 리뷰하며, 지적 사항은
둘이 알아서 정리합니다. Sno Station의 Reach 프로그램이 필요합니다. 프롬프트가 그것부터 확인합니다.

```text
Install only the tag-team skill from https://github.com/sno-ai/sno-station-skills
for this project. Check that `sno reach pair --help` works and tell me what is missing
before installing anything else.
```

Sno Station이 지원하는 에이전트는 Claude Code, Codex, Cursor, Hermes Agent, OpenClaw입니다. 스킬마다
에이전트에게 무엇이 필요한지 선언해 두었고, 설치 과정은 그 선언을 보고 스킬을 온전히 설치할지,
기능을 줄여 설치할지, 에이전트가 실행할 수 없어 건너뛸지 정합니다.

업데이트는 알아서 됩니다. `sno`는 새 릴리스를 발견하면 스스로 업데이트합니다. 전체 명령 목록은
[Sno Station 명령 레퍼런스](https://github.com/sno-ai/sno-station/blob/main/docs/sno-commands.md)에 있습니다.

### J · 리뷰와 감사

*동료끼리 서로의 작업을 검토하고, 감사를 통과하기 전엔 끝난 게 아닙니다.*

#### [peer-review](../../skills/J-peer-review-and-audit/peer-review/) — 다른 벤더의 리뷰어, 그리고 깨끗해질 때까지 도는 수정 루프

- **진짜로 독립적입니다.** 리뷰는 작성자의 대화가 하나도 없는 새 세션에서 돌고, 가능하면 다른
  벤더의 CLI를 씁니다. CLI가 하나뿐이어도 새 세션에서 돌아가며, 같은 벤더 리뷰였다는 사실을 첫
  줄에 밝힙니다.
- **실제로 비싼 문제부터 잡습니다.** 희한한 엣지 케이스에 1분이라도 쓰기 전에, 여러분의 시스템이
  실제로 만들어 내는 입력으로 평범한 경로부터 걸어 봅니다. 데이터 유실, 조용히 틀린 결과, 망가진
  메인 흐름이 먼저고, 코드 스타일은 목록에 없습니다.
- **모든 지적은 자기 자리를 증명해야 합니다.** 실제 사용자가 어떻게 그 지점에 닿는지, 무엇이
  깨지는지, 그리고 스스로 반박해 보려는 정직한 시도까지 적습니다. 리뷰어가 한 말은 버리거나
  누그러뜨리지 않습니다. 오탐으로 의심되는 건 숨기지 않고 표시합니다.
- **더하기 전에 덜어 냅니다.** 변경이 보탠 것 중 아무도 필요로 하지 않았던 걸 맨 먼저 나열하고,
  "지금 꼭 고칠 것"과 "그 밖에 발견한 것"을 따로 둡니다. 그래서 리뷰가 새 코드 더미로 변하지
  않습니다.
- **문서도 봅니다.** 스펙, 계획, 마이그레이션 매니페스트는 구조화된 보고서로 받습니다. 구현하는
  사람이 엉뚱한 걸 내보내게 만들 지점이 무엇인지.

*이럴 때:* 변경이나 계획, 스펙을 끝냈고 반영하기 전에 검토받고 싶을 때.

#### [less-is-more](../../skills/J-peer-review-and-audit/less-is-more/) — 돌아가는 최소한의 코드, 나머지는 칼로

- **한 줄 쓰기 전에 사다리를 오릅니다.** 정말 필요한가, 저장소에 이미 있나, 표준 라이브러리가
  해 주나, 플랫폼이 해 주나, 설치된 의존성이 해 주나. 그다음에야 돌아가는 최소한의 코드.
- **에이전트가 과하게 지은 걸 잘라 냅니다.** 구현이 하나뿐인 인터페이스, 절대 안 바뀌는 값에 붙은
  설정 손잡이, "나중을 위한" 뼈대, 진짜 일을 막아서는 검사와 관문.
- **테스트 예산을 아껴 씁니다.** 안심하려고 전체 스위트를 돌리는 대신, 변경을 증명하는 가장 작은
  테스트.
- **양방향을 알아서 오갑니다.** "write"나 "fix"면 만들고, "review"나 "simplify"면 자릅니다.
  만든 뒤에는 넘기기 전에 자기 diff부터 잘라 냅니다.

*이럴 때:* 모든 코딩 작업. 또는 "너무 복잡해", "뭘 지울 수 있지?"라고 말할 때.

#### [owner-intent-audit](../../skills/J-peer-review-and-audit/owner-intent-audit/) — 이게 정말 내가 말한 건가?

- **단어가 아니라 뜻을 확인합니다.** 계획이 여러분이 쓴 명사를 하나도 빠짐없이 쓰면서도 전혀 다른
  제품을 그릴 수 있습니다. 조건이 붙어 있던 게 무조건이 된 것, 예시였던 게 경계 전체가 된 것,
  금지 조항이 슬그머니 사라진 것을 잡아냅니다.
- **에이전트가 남기고 간 빚을 찾습니다.** 아무도 시키지 않은 작업, 현실과 더는 맞지 않는 문서,
  누구도 내릴 수 없는 결정, 근거 없는 "다 했어요".
- **계획이든 코드든.** 요구사항 문서, 설계, 작업 목록, 테스트 계획, 혹은 에이전트가 쓴 diff.

*이럴 때:* 계획을 승인하거나 에이전트의 작업을 머지하기 전에.

#### [agentic-walkthrough](../../skills/J-peer-review-and-audit/agentic-walkthrough/) — 전부 "성공"이라는데, 왠지 찜찜할 때

- **어떤 테스트도 못 잡는 조용한 실패를 위해.** 시작하고, 끝나고, 트레이스도 남기고, 자기 검사도
  통과했는데 정작 아무것도 건드리지 않은 작업.
- **프로그램 자리에 앉아 봅니다.** 경로를 한 단계씩 걸으며, 일을 조용한 헛손질로 바꿀 수 있는
  스위치, 기본값, 폴백을 하나하나 찾아냅니다.
- **단계마다 스스로 증명하게 합니다.** 진짜로 일했을 때만 나올 수 있는 좁은 관찰 하나로. 저장된
  행, 실제로 열린 데이터베이스 파일, 실제로 나간 API 호출.

*이럴 때:* 실행이 성공했다고 보고했는데, 정말 일을 했다는 증거가 필요할 때.

#### [first-principles-review](../../skills/J-peer-review-and-audit/first-principles-review/) — 코드가 되기 전에 아이디어부터 따져 묻기

- **먼저 조사합니다.** 그다음 제안된 해법을 빌리지 않고, 여러분에게 실제로 필요한 게 뭔지 처음부터
  다시 끌어냅니다.
- **모든 제약을 분류합니다.** 절대적 한계인지, 오너의 선호인지, 물려받은 습관인지. 무게를 받치는
  가정은 하나하나 증거에 대 봅니다.
- **분명한 판정 하나로 끝냅니다.** 진행, 재정의, 단순화, 교체, 분할, 먼저 테스트, 중단 중 하나.
  권장 방향과, 그 판정을 뒤집을 만한 증거도 함께.
- **깔끔하게 넘깁니다.** 다음에 요구사항을 쓸 사람이 바로 쓸 수 있는 보고서와 구조화된 요약.

*이럴 때:* 설계나 제품 아이디어가 계획으로 굳어지기 직전. 이름을 불러서 시작합니다.

#### [e2e](../../skills/J-peer-review-and-audit/e2e/) — 진짜 이유로만 실패하는 엔드투엔드 테스트

- **`e2e-environment-preflight`** 스킬은 첫 테스트가 돌기 전에 외부 서비스, 호스트, 브라우저 세션, 모델
  엔드포인트, 에이전트를 점검합니다. 긴 스위트가 죽은 의존성 하나 때문에 실패하는 일이 없도록.
- **`e2e-red-triage`** 스킬은 사전 점검이 예측하지 못한 드문 실패를 맡습니다. 찍기를 멈추고, 결과를
  두 쪽으로 가릅니다(접수됨 대 완료됨, 멈춤 대 크래시, 비어 있음 대 읽을 수 없음). 그다음 판정합니다.
  제품 버그인가, 새 환경 점검이 필요한가.

*이럴 때:* 실제 서비스를 상대로 엔드투엔드 스위트를 돌릴 때.

#### [test-writer](../../skills/J-peer-review-and-audit/test-writer/) — 정말로 빨간불이 들어올 수 있는 테스트

- **목보다 실물.** 저장소가 제공할 수 있다면 진짜 파서, 파일 시스템, 데이터베이스, 서비스를 씁니다.
  테스트 대상 자체를 목으로 대신하는 일은 없습니다.
- **모든 단언은 실패할 수 있어야 합니다.** 호출 횟수가 아니라 반환된 내용, 저장된 상태, 실제 부수
  효과를 확인합니다. 테스트를 통과시키려고 단언을 느슨하게 만드는 일은 절대 없습니다.
- **쓴 것만 돌립니다.** 전체 스위트가 아니라 바뀐 테스트에 맞는 가장 좁은 명령. 보고서에는 무엇을
  돌렸고 무엇이 나왔는지 적습니다.

*이럴 때:* 에이전트에게 테스트, 픽스처, 평가를 쓰거나 고치라고 할 때. Sno Station 없이 단독으로
돌아갑니다.

#### [cross-vendor-security-audit](../../skills/J-peer-review-and-audit/cross-vendor-security-audit/) — 버린 것을 다시 읽는 보안 감사

**Claude가 세 번 훑고도 공개된 고위험 버그를 놓쳤습니다. Claude가 버린 것을 Codex가 한 번 훑고
찾아냈습니다.** 이 버그에서는 Claude가 한 번 더 볼 때마다 버렸던 이유를 그대로 되풀이했고, 다른
벤더는 다른 이유를 가져왔습니다.

follow-redirects 1.16.1을 감사했습니다. 알려진 버그가 있는 버전입니다
([GHSA-mrwp-f3q8-3g9p](https://github.com/advisories/GHSA-mrwp-f3q8-3g9p), 고위험, 1.16.2에서 수정).
다른 JavaScript realm에서 만든 비밀 헤더 목록을 빈 목록으로 취급하는 바람에, 호출자의 API 키가
리다이렉트를 따라 다른 호스트로 넘어갑니다.

- Claude, 첫 번째 감사: 보지도 못했습니다.
- Claude, 두 번째 감사: 봤지만 "보안 강화 사항이지 취약점은 아님"으로 분류했습니다.
- 제쳐 둔 것을 전부 다시 읽은 새 Claude: 동의. "호출자의 오용".
- Codex 단독 감사: 보지도 못했습니다.
- **Claude가 제쳐 둔 것을 다시 읽은 Codex: 반대했고, 소스를 따라 추적한 뒤 검증으로 되돌려
  보냈습니다.**

이 마지막 단계가 이 스킬이 Cloudflare의 security-audit 스킬에 더한 부분입니다(MIT 라이선스로 사용.
감사 방식, 증거 기준, 검증기, 보고서는 같습니다). 보고서를 내기 전에, 다른 벤더의 모델이 감사가
제쳐 둔 항목을 읽기 전용으로 하나도 빠짐없이 다시 읽고 전부 답해야 합니다. 그 모델이 되살린 건
다시 검증합니다. 검증에서 또 기각되면 보고서는 그 항목을 "리뷰어 의견 불일치" 아래에 양쪽 이유와
함께 올리고, 판단은 여러분이 합니다.

프로젝트 둘, 알려진 버그 셋. 비율이 아니라 사례입니다. 다른 프로젝트에서는 어느 벤더의 리뷰어든
버그를 되찾았습니다. Claude의 첫 감사가 그 버그를 아예 들여다보지 않았을 때는, 그 감사를 다시
읽어도 찾지 못했습니다.

*이럴 때:* 코드베이스 전체 보안 감사가 필요할 때. Sno Station이 있으면 아직 사용량이 남은 다른 벤더
리뷰어를 고릅니다. 없으면 Claude Code에서는 Codex를, Codex에서는 Claude Code를 부르고, 벤더가
하나뿐이었으면 그렇다고 밝힙니다.

### M · 빌드와 배포

*어떤 워크스테이션에서든 한 번에 팀을 세팅하고, 일에 필요한 걸 만들고, 모든 머신에 퍼뜨립니다.*

세팅 자체는 스킬이 아니라 `sno setup` 명령입니다. 이 중 두 개는 머신을 건강하게 유지하고 에이전트가
`sno` 명령을 쉽게 다루게 해 주며, 나머지는 코드를 씁니다. 하나는 Codex에게 넘기고, 넷은 Shell,
TypeScript, Python, Rust로 씁니다.

#### [medic](../../skills/M-build-and-rollout/medic/) — 에이전트 팀, 괜찮은가? 답은 한 줄씩.

- **팀에 필요한 걸 전부** 10초쯤에 점검합니다. 도구 설치, 스킬 설치, 스킬 명령 실행 가능 여부, 훅
  설정, 메시징 작동, 두 벤더 사용량 조회 가능 여부, 임시 공간 여유.
- **문제마다 해결책이 붙습니다.** `WARN` 또는 `FAIL`, 무엇이 잘못됐는지, 그리고 고치는 정확한 명령.
- **읽기만 하고 손대지 않습니다.** 설치도, 수리도, 시작도, 중지도 하지 않습니다. 무엇을 고칠지는
  여러분이 정합니다.

*이럴 때:* 새 머신에서, 에이전트끼리 연락이 안 될 때, 긴 실행이 시작되지 않을 때.

#### [sno-cli](../../skills/M-build-and-rollout/sno-cli/) — 에이전트가 `sno`를 처음부터 제대로 다룹니다

- **낡을 일이 없습니다.** 에이전트는 기억이 아니라 설치된 `sno`에서 직접 정확한 명령과 플래그를
  읽습니다.
- **작업 지도와 레시피.** 설치, 업데이트, 상태 점검, 계정, 스킬, 야간 루프.
- **선택은 여러분 몫.** 도구를 조작할 뿐, 여러분 대신 설정을 정하지 않습니다.

*이럴 때:* 에이전트에게 Sno를 설치, 업데이트, 점검, 설정하라고 할 때.

#### [codex-coder](../../skills/M-build-and-rollout/codex-coder/) — 계획은 Claude가, 코드는 Codex가

- **세션 하나, 벤더 둘.** Claude Code가 계획과 대화를 쥐고, 코딩은 평범한 `codex exec` 실행으로
  돌립니다. 비싼 모델이 타자를 치지 않게요.
- **언어는 알아서 고릅니다.** 작업이 건드리는 파일을 보고 Shell, TypeScript, Python, Rust 중에서.
  여러분의 언어 스킬이 설치돼 있으면 그걸 씁니다.
- **멈춘 실행은 잡아냅니다.** 실행 중에는 Claude Code에 진행 상황이 전달되고, 15분 동안 아무것도
  쓰지 않은 실행은 종료한 뒤 한 번 더 시작합니다.

*이럴 때:* 코딩이 절반쯤 왔는데 Claude 사용량이 바닥났을 때, 혹은 Claude가 세운 계획을 Codex가 짜게
하고 싶을 때. Claude Code 쪽에는 Sno Station의 `heartbeat`가 필요합니다.

#### [shellscript-coder](../../skills/M-build-and-rollout/shellscript-coder/), [ts-coder](../../skills/M-build-and-rollout/ts-coder/), [python-coder](../../skills/M-build-and-rollout/python-coder/), [rust-coder](../../skills/M-build-and-rollout/rust-coder/) — 들어갈 저장소에 딱 맞는 코드

- **쓰기 전에 읽습니다.** 저장소의 런타임, 버전, 헬퍼, 호출부, 테스트부터 봅니다. 그래서 새 코드가
  주변 코드와 같은 얼굴을 합니다.
- **일부러 작게.** 호환성 심 없음, 아무도 요청하지 않은 옵션 없음, 두 파일 건너에 이미 있는 헬퍼를
  또 만들지 않음.
- **명령이 통과해야 끝.** 보고서의 모든 주장은 여러분의 저장소에서 실제로 돌린 검사로 이어집니다.
  실패한 검사를 두고 다 했다고 보고하는 일은 없습니다.

*이럴 때:* 이 네 언어 중 하나로 프로덕션 코드를 쓰거나 고치게 하고 싶을 때. Sno Station 없이 단독으로
돌아가고, `codex-coder`가 작업마다 맞는 것을 고릅니다.

### S · 소통과 인수인계

*공유 우편함으로 대화하고, 누가 자리를 비우면 다른 사람이 맥락 그대로 이어받습니다.*

이 스킬들은 Sno Station이 설치하는 메시징 계층, Sno Reach 위에서 돌아갑니다. 에이전트마다 주소가
생기고, 다른 에이전트의 우편함에 보관형 메시지를 보내고, 다른 에이전트를 깨워 읽게 할 수 있습니다.
데몬도, 서버도 없습니다.

#### [handoff](../../skills/S-communication-and-handoff/handoff/) — 하나도 흘리지 않는 인수인계

- **상태를 통째로 담습니다.** 끝낸 것, 하다 만 것, 커밋하지 않은 변경, 이미 내린 결정, 손대면 안
  되는 범위.
- **넘겨받는 쪽은 인계 확인이 끝날 때까지 아무것도 쓰지 않습니다.** 그래서 두 에이전트가 같은 작업을
  동시에 고치는 일이 없습니다.
- **넘기는 쪽은 진짜로 손을 뗍니다.** 인계 후에는 멈춥니다. 주인이 둘이 되어 기웃거리는 일은 없습니다.
- **넘기는 쪽이 이미 사라져도 됩니다**(사용량 거부, 크래시, 닫힌 창). `sno handoff-checkpoint`
  진행 기록이 있으면 새 에이전트가 첫 번째 미완료 작업부터 이어 갑니다.

*이럴 때:* 한 에이전트가 자기 일을 다른 에이전트에게 넘겨야 할 때.

#### [rotate-agent](../../skills/S-communication-and-handoff/rotate-agent/) — 사용량 한도 때문에 긴 실행을 날리는 일은 이제 그만

- **넘기는 쪽이 아직 살아 있을 때 움직입니다.** 몇 분마다 남은 사용량을 지켜보다가 기준선에서
  넘깁니다. 거부당한 뒤, 인수인계서를 쓰기엔 이미 늦은 때가 아니라.
- **방향은 양쪽 다.** Codex에서 Claude Code로, 또는 Claude Code에서 Codex로.
- **선을 지킵니다.** 한 번만 발동하고, 감시를 얼마나 오래 돌릴지 정해 둘 수 있습니다.
- **타이밍을 놓쳤을 때의 안전망.** 넘길 타이밍을 놓쳤다면, `sno rotate-agent-resume`이 디스크의
  진행 기록에서 대신할 에이전트를 시작합니다.

*이럴 때:* 한 벤더의 사용량이 바닥나도 긴 실행은 끝나야 할 때. 두 CLI 모두 로그인돼 있어야 하고
tmux가 필요합니다.

#### [subscription-quota-check](../../skills/S-communication-and-handoff/subscription-quota-check/) — 사용량이 얼마나 남았는지, 하나도 쓰지 않고

- **최악의 습관을 끊습니다.** 실제 호출을 날려 보고 에러 메시지를 읽어서야 한도가 끝난 걸 아는 것.
- **Claude Code와 Codex를 한꺼번에** 8초쯤에 읽고, 언제 사용량이 초기화되는지 알려 줍니다.
- **묵은 숫자엔 솔직합니다.** 지금 값인지 마지막으로 알려진 값인지 확인하고, 어느 쪽인지 밝힙니다.
- **혼자서 주기적으로 조회하지 않습니다.** 그래서 스스로 요청 제한에 걸릴 일이 없습니다.

*이럴 때:* 여러분이 물어볼 때, 또는 벤더가 작업을 거부한 직후.

#### [heartbeat](../../skills/S-communication-and-handoff/heartbeat/) — 긴 실행의 진행 상황을 대화창으로 배달

- **두 가지 형태.** N분마다 보고(학습, 긴 빌드, 생성 큐), 또는 뭔가 끝날 때까지 지켜보기.
- **정한 시각의 작업.** 에이전트에게 날짜나 시각을 말하세요. 한 번이든 반복이든. 작업을 적어 두고,
  대화가 닫힌 뒤에도 그 시각에 에이전트가 시작합니다.
- **알림은 여러분이 있는 곳으로.** 매번 측정값은 아무도 안 읽는 로그가 아니라 에이전트의 대화창에
  도착합니다.
- **잘못 쓰기 어렵습니다.** 간격 단위는 분입니다. 초 단위 같은 숫자를 넣으면 몇 초마다 에이전트를
  조용히 깨우는 대신 거부합니다.

*이럴 때:* 긴 작업을 지켜보는 사람 없이 돌리면서 소식은 듣고 싶을 때, 또는 여러분이 없을 시각에
해야 할 일이 있을 때.

#### [reach](../../skills/S-communication-and-handoff/reach/) — 에이전트끼리 대화합니다

- **Claude Code나 Codex 에이전트를 시작합니다.** 자기 주소와 작업 폴더를 가진 채로.
- **일을 보내고 답장을 읽습니다.** 보관형 메시지로, 아니면 살아 있는 에이전트와 바로 지금.
- **메시지에 추가 권한은 없습니다.** 메시지가 여러분이 준 작업 범위를 넓히는 일은 없습니다.

*이럴 때:* 한 에이전트가 다른 에이전트에게 연락하거나, 시작시키거나, 기다려야 할 때.

#### [join-talk](../../skills/S-communication-and-handoff/join-talk/) — 명령 하나로 어떤 에이전트든 연락 가능하게

- **출력은 한 줄.** `joined <address>`. 다른 에이전트에게 그 주소를 알려 주면 이 터미널에 닿을 수
  있습니다.
- **반복해도 안전합니다.** 같은 터미널에서 다시 실행해도 바뀌는 게 없습니다.
- **거절은 분명하게.** 안 될 때는 왜 안 되는지 정확히 말합니다.

*이럴 때:* 에이전트를 손으로 열었는데 다른 에이전트가 연락할 수 있게 하고 싶을 때.

#### [tag-team](../../skills/S-communication-and-handoff/tag-team/) — 한 작업에 에이전트 둘, 하나는 만들고 하나는 리뷰

- **명령 하나.** `sno reach pair "the task"`가 현재 폴더에서 두 에이전트를 시작합니다. 각자 tmux
  창에 떠 있어서 열어 보고 지켜볼 수 있습니다.
- **여러분에게 오기 전에 둘이 먼저 다툽니다.** 리뷰어는 결과와 바뀐 파일을 읽고, 구체적인 결함이나
  명시적인 "결함 없음"으로 답합니다. 둘은 수정과 리뷰를 계속 주고받고, 여러분의 에이전트는 깨끗하다고
  하기 전에 리뷰어에게 확인합니다.
- **어떤 리뷰를 받았는지 밝힙니다.** 두 벤더에 로그인돼 있으면 리뷰는 다른 쪽이 합니다. 하나뿐이어도
  페어는 돌아가고, 리뷰가 같은 벤더 안에서 이뤄졌다고 알려 줍니다.
- **섣불리 깨끗하다고 하지 않습니다.** 첫 리뷰에 지적이 있으면 미해결로 보고합니다. 세 번째 리뷰어를
  부르지 않고, 첫 리뷰가 아직 안 왔다고 페어를 하나 더 띄우지도 않습니다.

*이럴 때:* 다른 의견을 들어 볼 만한 작업인데, 에이전트 사이를 직접 오가며 전달하고 싶지는 않을 때.

### H · 보고와 가시성

*누가 무엇을 끝냈는지, 누가 무엇을 잡았는지, 누가 누구 대신 뛰었는지, 무엇이 진행 중인지 다 보입니다.*

#### [away-brief](../../skills/H-reporting-and-visibility/away-brief/) — 돌아오면 딱 한 페이지

- **네 칸, 최대 60줄.** Done, Stuck, Needs you, Spend.
- **여러분을 기다리는 일은** 끝난 일의 긴 목록에 밀려 페이지 밖으로 사라지지 않습니다.
- **"다 했다"는 실제인 것만.** git에 있거나, 납품된 작업 지시서에 있거나, 끝난 진행 기록에 있는 것.
  에이전트가 했다고 말한 것은 아닙니다.
- **밤사이 얼마를 썼는지 보여 줍니다.** 자리를 뜨기 전에 `sno away-brief mark`를 실행하면, 다음
  페이지에 그 뒤로 쓴 사용량이 나옵니다.

*이럴 때:* 자고 일어나서, 회의가 끝나고, 지켜보지 않은 긴 실행이 끝난 뒤.

#### [catch-report](../../skills/H-reporting-and-visibility/catch-report/) — 두 번째 에이전트, 값을 하나? 숫자로 답합니다.

- **두 개의 숫자를 나란히.** 다른 모델이 리뷰에서 잡은 문제, 그리고 에이전트가 자기 실수를 스스로
  잡은 순간.
- **부풀리지 않습니다.** 둘은 따로 두고 절대 합치지 않습니다. 측정할 수 없었던 부분은 0으로 적는
  대신 측정 못 했다고 밝힙니다.
- **가장 큰 건을 제목째 인용합니다.** 이미 여러분 머신에 있는 리뷰 기록에서.

*이럴 때:* 한 주의 리뷰 결과가 궁금할 때, 혹은 에이전트를 둘 돌리는 이유를 설명해야 할 때.

#### [agentic-time-estimate](../../skills/H-reporting-and-visibility/agentic-time-estimate/) — 에이전트 작업의 진짜 견적

- **사람 개발자 시간이 아니라 에이전트의 실제 소요 시간.** 이 일이 에이전트에게 얼마나 걸릴지, 돌고
  있는 작업이 얼마나 더 걸릴지. 짐작하기 전에 먼저 잽니다.
- **믿을 수 있는 시각.** 여러분에게 보여 주는 시각은 전부 `sno report-time`에서 나오고, 여러분의
  시간대 옆에 UTC가 함께 붙습니다.

*이럴 때:* "얼마나 걸려?", "언제 끝나?"라고 물을 때.

### T · 위임과 작업 지시

*리드가 일을 작업 지시서로 나눠 주고, 누가 어떤 일을 맡을지 정합니다.*

#### [charter](../../skills/T-delegation-and-work-orders/charter/) — "다 했다"의 뜻을 적은 파일 하나

- **여러분의 말을 지킵니다.** 결정, 사실, 요구사항을 지어내지 않고, 답에 따라 결과가 달라질 때만
  한 번에 질문 하나씩 묻습니다.
- **돌려 볼 수 있는 성공 기준.** 기준마다 무엇을, 어디서, 어떻게 관찰할지 적고, 통과/실패로 답합니다.
- **형식주의 없음.** 무슨 실패를 잡는지 누구도 댈 수 없는 항목은 넣지 않습니다.
- **어떤 프로젝트든.** 소프트웨어, 문서, 캠페인, 리서치, 운영.

*이럴 때:* 다른 누군가가 하기 전에 글로 된 브리핑이 필요한 일.

#### [deliver](../../skills/T-delegation-and-work-orders/deliver/) — charter를 증명된 결과까지 끌고 가기

- **charter의 기준이 곧 완료의 정의입니다.** 그 밖의 것은 아닙니다.
- **모든 기준은 기록이 남는 실제 실행으로 증명합니다.** `sno deliver-proof`로 추적합니다.
- **독립 리뷰 한 번,** 그리고 정직한 마무리. 무엇이 통과했고, 무엇이 안 됐고, 왜인지.
- **남이 멈춘 자리에서 이어 갑니다.** 앞선 에이전트가 진행 기록을 남겼으면, 처음부터 다시 하지 않고
  다음 미완료 단계부터 이어 갑니다.

*이럴 때:* charter가 확정됐고, 누군가 그 일을 해야 할 때.

#### [pl](../../skills/T-delegation-and-work-orders/pl/) — 업무 라인 하나를 맡는 Project Lead 에이전트

- **실행 에이전트를 최대 넷까지 돌립니다.** 하나에 charter 하나씩, 순차로든 병렬로든.
- **딸린 스킬 다섯 개.** `pl-dispatch`는 일을 열고 일정을 잡고, `pl-watch`는 돌고 있는 에이전트를
  감독하고, `pl-audit`는 무엇이든 닫기 전에 인수 여부를 확인하고, `pl-env`는 일이 돌아가는 환경을
  고치고, `pl-analyze`는 문제가 생기면 근본 원인 분석을 씁니다.

*이럴 때:* 한 프로젝트에 여러 에이전트가 한 리드 아래에서 일해야 할 때. 이름을 불러서 시작합니다.

#### [cos](../../skills/T-delegation-and-work-orders/cos/) — 비서실장: 여러분이 대화하는 단 하나의 에이전트

- **여러분에겐 대화창 하나,** 여러분의 언어로. Project Lead 한 명에서 세 명까지 병렬로 조율하고,
  여러분에게는 어려운 결정만 가져옵니다. 돈, 방향, 레드라인.
- **딸린 스킬 세 개.** `cos-watch`는 모든 Project Lead가 살아서 일정대로 움직이게 하고,
  `cos-review`는 여러분이 돌아왔을 때 밤사이 내린 결정을 한 번에 검토하고, `cos-evolve`는 되풀이되는
  관리 실패를 강제되는 규칙으로 바꿉니다.

*이럴 때:* 여러 갈래의 일을 돌리면서 창구는 하나로 두고 싶을 때. 이름을 불러서 시작합니다.

### R · 회고와 개선

*팀이 자기 일을 돌아보고, 교훈을 규칙과 더 나은 관행으로 바꿉니다.*

#### [rem-reflect](../../skills/R-recursive-self-improvement/rem-reflect/) — 야간 루프: 에이전트가 자기 세션에서 배웁니다

- **하루 한 번,** 이 머신의 에이전트 세션(Claude Code, Codex, Cursor, Hermes Agent, OpenClaw)을 읽고,
  되풀이되는 실패와 교정을 찾아 교훈과 스킬 수정 제안으로 만듭니다.
- **모든 건 여러분이 승인합니다.** 하나하나에 `sno rem-reflect accept`, `reject`, `tbd`. 여러분의
  accept 없이는 아무것도 바뀌지 않습니다.
- **교훈은 필요할 때 돌아옵니다.** 승인된 교훈은 다음 세션을 시작할 때 에이전트에게 보여 줍니다. 이
  프로젝트에만, 또는 모든 프로젝트에.
- **머신 밖으로 무엇이 나갈지는 여러분이 정합니다.** `local-first` 모드에서는 Sno로 아무것도 보내지
  않습니다. 교훈 초안을 쓰려고 그날 밤 세션 몇 개가 여러분 자신의 Claude Code나 Codex 계정으로만
  갑니다. 나머지 두 모드에서는 기본 공유 수준일 때, 더 나은 판단을 위해 세션 텍스트(흔한 비밀 값은
  먼저 가립니다. 단, 완벽을 장담하진 않는 최선의 노력 수준)와 설치된 스킬을 Sno 클라우드에 올립니다. 업로드는 언제든
  `sno station consent off`로 끌 수 있습니다. 스킬은 무엇을 읽고 무엇을 보내는지 정확히 나열합니다.

딸린 스킬인 `pl-analyze`(Project Lead의 사고 분석)와 `cos-evolve`(반복되는 실패를 규칙으로)도 여기에
속합니다. 둘은 `pl`, `cos`와 함께 배포됩니다.

*이럴 때:* 항상 켜져 있습니다. `sno setup`이 하루 한 번 실행을 걸어 둔 뒤부터.

## 믿고 쓰게 만든 방식

릴리스에 들어간 모든 배포 단위는 공개되기 전에 똑같은 검사를 통과했습니다.

1. 저장소에 `LICENSE`와 `NOTICE`가 있다.
2. 배포 단위는 딸린 스킬과 에이전트별 차이까지 고스란히, 통째로 복사된다.
3. 개인적인 건 하나도 남지 않는다. 홈 경로, 오너 이름, 내부 호스트, 하드코딩된 모델이 없고, 한국어·
   중국어·일본어 문자도 없다.
4. 모든 스킬의 헤더가 파싱되고, 에이전트에게 필요한 것을 적은 선언이 유효하다.
5. 각 스킬의 자체 테스트가 작성자의 머신이 아니라 그 깨끗한 사본에서 통과한다.
6. 도장인 `PUBLISHED.json`이 맨 마지막에 쓰인다. 자체 테스트 개수, 그리고 계약과 페이로드의
   다이제스트가 담긴다.

검사 하나라도 떨어진 스킬은 공개되지 않습니다. 도장은 손이 아니라 릴리스 빌드가 씁니다. 스킬
텍스트는 전부 영어지만, 에이전트는 여러분이 말을 거는 언어가 무엇이든 그대로 따릅니다.

## 이 스킬과 Sno Station

스킬은 습관입니다. [Sno Station](https://github.com/sno-ai/sno-station)은 그 습관을 돌리는
워크스테이션입니다. 스킬들이 같이 쓰는 메모리, 인수인계를 터뜨리는 사용량 감시, 에이전트 사이의
메시지, 교훈을 써 내는 야간 실행. Sno Station을 설치하면 여기 있는 스킬도 전부 같이 들어옵니다.

| 원하는 것 | 가는 곳 |
|---|---|
| 워크스테이션 전체, 그리고 지금 어느 에이전트에서 무엇이 돌아가는지 | [sno-ai/sno-station](https://github.com/sno-ai/sno-station#what-you-can-use-today-and-where-it-stops) |
| 창과 컴퓨터를 넘나들며 메시지를 주고받는 에이전트 | [Sno Reach](https://github.com/sno-ai/sno-station/blob/main/apps/reach/README.md) |
| 여러분이 정한 시각에 시작되는 일 | [Finish](https://github.com/sno-ai/sno-station/blob/main/docs/finish.md) |
| 스킬이 호출하는 모든 `sno` 명령 | [명령 레퍼런스](https://github.com/sno-ai/sno-station/blob/main/docs/sno-commands.md) |
| 위 이야기들 뒤의 원본 기록 | [증거 폴더](https://github.com/sno-ai/sno-station/tree/main/docs/evidence) |
| 질문하거나, 만든 걸 자랑하고 싶을 때 | [Discussions](https://github.com/sno-ai/sno-station-skills/discussions) |
| 처음 해 볼 만한 작은 기여 | [Good first issues](https://github.com/sno-ai/sno-station-skills/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22)와 [CONTRIBUTING.md](../../CONTRIBUTING.md) |

**그리고 두 저장소 모두에 스타를.** 저희는 이 스킬로 Sno Station을 만듭니다. 저희의 야간 근무에서
배운 것이 릴리스마다 여기에 실립니다.

## 스킬 만드는 분들께

### 디렉터리 구조

```
skills/
  README.md                     the category index
  <category>/<unit>/
    skill/                      one skill: SKILL.md, references/, scripts/
    skills/<member>/            or a family of skills that ship together
    overlay/claude|codex/       per-agent differences, when a skill needs them
    public-bin/                 one file per `sno <file name>` command the skill provides
    PUBLISHED.json              the stamp, written into the release archive by the build
registry.yaml                   unit -> category code (and tier)
scripts/
  requirements-contract.json    the contract every requires: block is checked against
LICENSE                         Apache-2.0
```

분류 코드는 고정이고, 순서는 J M S H T R입니다. 디렉터리 이름과 `registry.yaml`에 쓰입니다.

### 스킬에 필요한 것 선언하기

모든 `SKILL.md`는 `requires:` 블록으로 시작합니다. `sno setup`은 이걸 읽고 에이전트별로 스킬을
설치할지 정합니다.

```yaml
requires:
  programs:
    - {name: reach, min_version: "2.0"}                          # Sno Station programs the skill calls
  harness:
    - {slot: 4.shell, need: required}        # what the agent itself must be able to do
```

- **programs**는 스킬 옆에 설치되어 `sno <name>`으로 실행되는 Sno Station 프로그램입니다.
  `reach`, `heartbeat`, `subscription-quota-check`, `report-time`.
- **min_version**은 스킬이 요구하는, 지정한 Sno Station 프로그램의 최소 버전입니다.
- **slots**는 에이전트의 능력 이름입니다. `4.shell`(셸 명령 실행), `4.file-read-write`(파일 읽기와
  쓰기), `4.background-processes`(명령을 백그라운드에서 실행), `2.pre-turn-context-injection`(매 턴
  전에 에이전트 컨텍스트에 텍스트 추가), `3.reader-to-agent-delivery`(백그라운드 리더의 출력이
  에이전트에게 도달).
- **need**는 `required`(그 슬롯이 없는 에이전트는 스킬을 받지 않음), `preferred`(스킬은 설치되고
  기능을 줄여 동작), `optional`(편의 기능일 뿐) 중 하나입니다.
